Summary

Each agent gets a connection that you set up in Claire: a name, the chats it can see, the things it may do, and a token lifetime. You can change those settings at any time, and they apply on the agent's next request without a new token.

The rule behind the write tools: an agent can never increase what any connection can read. No tool touches chats.ai_enabled or connection settings, and a group's type never grants access. Permissions explains why this matters.

Not included: sending messages without your approval, media bytes, and an ask_claire tool (your agent already has a model). This is also separate from the plugin system's remote_mcp runtime, where Claire is the MCP client calling other servers.

Decisions for you

You've settled per-token settings, lifetime set at creation, starting with your account only, approval-only replies, and showing only saved searches. One choice remains. The spec is written around the recommended answer.

What does "write access to messages" mean?

Decided: agents can propose a reply, and you approve it in Claire. Nothing gets sent until you tap. This is how the loop agent already works, and the plugin docs require approval for outbound messages in v1.

Direct sending is not offered as a toggle. A message containing a prompt injection could then make the agent write to your real contacts from your real accounts, which you can't take back. If you want it later, it deserves its own review.

Which agent searches appear in the app?

Decided: only the ones an agent explicitly saves. Agents run many throwaway searches while working, and recording all of them would bury the useful ones. It would also keep a stored history of every query. A per-connection "show all searches" toggle can come later if you miss it.

Should agent-set group types show in your inbox?

Recommended: yes, marked as set by an agent. The label is only useful if you see it, and a visible source lets you spot a wrong one. Your own choice always wins, and an agent cannot overwrite it.

Agent connections

A connection holds the settings, and the token is only its credential. That separation is what lets you turn things on or off without reconfiguring the agent, and lets OAuth reuse the same settings later.

Create token
  1. Name. Which agent this is for, such as "Claude Code, laptop". It appears in activity and on anything the agent creates.
  2. Chats. Set 1:1 chats and groups separately, then hide any chats that should stay private. The group picker shows each group's type, member count, last activity and whether AI is on.
  3. Abilities. Read messages starts on. Everything that writes starts off.
  4. Lifetime. Pick a duration. One year is the maximum, because this token will sit in configuration files.
  5. Instructions (optional). Up to 1,000 characters passed to the agent, such as "Focus on work chats. My company is Acme."
  6. Review. A plain summary, such as "This agent can read 214 1:1 chats and 6 groups, set group types and save searches, until 31 January."
  7. Token. Shown once, with copy buttons for the connection commands.

Afterward

Opening a connection shows the same controls, editable, plus last-used time, messages read, chats touched and every change the agent made. You can undo a change, rotate the token, or revoke it.

Enabling your account

UPDATE public.users SET mcp_enabled = TRUE WHERE id = '<your-user-id>';

Turning the flag off stops every connection on the account at its next request. Opening this to others later means an operations console control or a plan check that sets the same flag.

Token and verification

A token is clr_mcp_ followed by 32 random bytes in base64url. The database stores a SHA-256 hash, which is sufficient for a random secret of this length, plus a short prefix so you can recognize it.

  1. Check the shape with a regex, so junk never reaches the database.
  2. Hash it and load the connection joined to users. Require mcp_enabled, revoked_at IS NULL and expires_at > NOW().
  3. Attach the connection's current settings to the request, so changes apply immediately.
  4. Update last_used_at at most once a minute.

A bad token gets 401 with WWW-Authenticate: Bearer error="invalid_token". The first release leaves out resource_metadata and the protected resource document, because advertising them would send clients into an OAuth flow that does not exist yet.

Why group type never grants access. A "share all my work groups" rule sounds convenient, but combined with set_group_type it would let an agent relabel any group as "work" and then read it. A connection limited to family groups could also gain a group because a different agent relabeled it. A wrong automatic classification would have the same effect.

So the picker's "Select all work groups" adds those specific groups once, and they stay fixed. A new group is never added automatically. This follows the warning already in group-classifier.ts: a classifier that switched processing on "would make every one of its mistakes a privacy incident".

Chat access

These rules apply to every tool and path, including context windows, direct lookups by ID, and write tools.

RuleBehavior
TenantEvery query uses the user_id from the connection, never from tool input.
Account AI switchIf isAiProcessingEnabled() returns false, all tools return ai_disabled. A failed read also blocks.
1:1 chatsai_enabled (default) covers all except those with AI turned off. Also selected or none.
Groupsai_enabled (default) covers groups you turned on. selected covers the ones you picked, all covers every group, and none covers nothing.
Explicit choicesPicking a group, or choosing all, includes groups with AI off. The picker shows this state so the choice is informed.
Hidden chatsAlways win, whatever other setting applies.
Deleted messagesExcluded everywhere, including context.
Out-of-scope IDsReturn not_found, the same as an ID that does not exist.

The rule lives in one SQL function, and every tool reads and writes through mcp_* functions that call it. With both settings on ai_enabled it matches chatAiProcessingEnabled(), and a test holds the two together.

CREATE FUNCTION public.mcp_chat_visible(conn public.mcp_connections, ch public.chats)
RETURNS BOOLEAN LANGUAGE sql STABLE AS $$
  SELECT ch.user_id = conn.user_id
    AND NOT ch.id = ANY(conn.hidden_chat_ids)
    AND (cardinality(conn.platforms) = 0 OR ch.platform = ANY(conn.platforms))
    AND CASE WHEN COALESCE(ch.is_group, FALSE) THEN
      CASE conn.group_access
        WHEN 'all'        THEN TRUE
        WHEN 'selected'   THEN ch.id = ANY(conn.selected_chat_ids)
        WHEN 'ai_enabled' THEN ch.ai_enabled IS TRUE
        ELSE FALSE
      END
    ELSE
      CASE conn.direct_access
        WHEN 'selected'   THEN ch.id = ANY(conn.selected_chat_ids)
        WHEN 'ai_enabled' THEN COALESCE(ch.ai_enabled, TRUE)
        ELSE FALSE
      END
    END;
$$;
-- Revoke EXECUTE on every mcp_* function from public, anon and authenticated.

Tools

Read tools declare readOnlyHint: true. Write tools declare readOnlyHint: false and destructiveHint: false. Each returns structuredContent with an outputSchema, and the same JSON as a text block for older clients. Phone numbers, media URLs and raw platform IDs are left out.

Items reference messages rather than copying them. Deleted messages drop out, edits show up, and no second copy of message text exists. Unlike activity, this stores the query, because the agent is deliberately handing it to you.

In the app

  • Search screen: a "From your agents" section in the empty state, newest first, with unviewed ones marked. Each row shows the title, result count and which agent made it.
  • Detail screen: title, "Created by Claude Code, laptop", summary, then messages rendered from the database. Tapping one opens the chat at that message. You can run it again or delete it.
  • Revoking an agent: its searches stay, because they are yours. You can delete them separately.

Routes, using your app session: GET /saved-searches, GET /saved-searches/:id, POST /saved-searches/:id/rerun and DELETE /saved-searches/:id. A rerun uses your account's full access, since you are the one viewing it, and the screen labels it as a search across all your chats.

Search

  1. Lexical. mcp_search_messages runs full-text search with the same 'simple' dictionary as Ask Claire. That dictionary does no stemming, so "meetings" will not match "meeting". Hybrid mode covers the gap.
  2. Semantic. Unless the mode is exact, the query is embedded and mcp_match_messages runs a vector search with the same 0.22 similarity floor as Ask Claire.
  3. Merge. Each list contributes up to 60 candidates, scored by reciprocal rank fusion with the existing 1 / (60 + rank + 1) formula. Pages come from that merged list, so the cursor is a validated offset.
  4. Context. A new mcp_read_messages function fetches neighbors by position and always includes the anchor.

If embedding fails, hybrid search falls back to exact results and reports it. If a caller explicitly asked for semantic, the tool returns search_unavailable, because silently substituting keywords would misrepresent the search.

Two performance risks to check first. Ask Claire's function filters on COALESCE(m.content, '') <> '', which Postgres probably cannot match to the predicate of idx_messages_content_fts, so that index may go unused today.

The vector index is one HNSW index across all users. Filtering to a single user after an approximate scan can return far fewer rows than requested. Run EXPLAIN ANALYZE on staging for both before settling the function bodies.

Security

Main risk: prompt injection through message content. Anyone who can message you can put instructions in front of your agent. With the write tools on, a manipulated agent could mislabel groups or save misleading searches. Claire's own damage stays limited, because those writes can be undone, contact no one and cannot widen access.

The larger risk sits outside Claire. An agent that also holds email, web or shell tools could send your messages somewhere, and this server cannot fully prevent that. For agents using this server, require approval on outbound tools.

Testing

Automated, with bun test

  • Auth: a session JWT is rejected on /mcp, an MCP token is rejected on /messages and /agent-connections, and expired, revoked, malformed and not-enabled tokens get 401. No token value appears in logs.
  • Tenancy: with two seeded users, each tool returns not_found or nothing for the other user's chat and message IDs, and the settings API refuses their chat IDs.
  • Access: a table of direct and group settings, hidden chats and platforms, checked against all read tools, including as context around a visible message.
  • Live settings: turning off a permission or hiding a chat takes effect on the next call without a new token.
  • No escalation: set_group_type on a hidden group returns not_found, setting a type never makes a group visible to any connection, and save_search rejects a hidden message ID.
  • Your choice wins: a user type is never replaced, and undo restores the previous value only if it has not changed since.
  • Policy parity: mcp_chat_visible with defaults matches chatAiProcessingEnabled across every null, true and false combination.
  • Fail closed: a preference read error returns ai_disabled, and Redis being unavailable returns 503.
  • Context: get_message always includes the anchor, in a chat with hundreds of messages in the same hour.
  • Transport: a bad Origin gets 403 rather than 500, and a header mismatch gets 400 with -32020.
  • Output: tag characters and bidi overrides are stripped, emoji sequences survive, and deleted messages never appear. Saved searches lose deleted messages.
  • Privacy: after a search, neither logs nor activity rows contain the query or message text.

The app

Verify the screens in the iOS Simulator and in the Electron app, as CLAUDE.md requires. A plain browser tab does not count. Check that the token is never cached, that the picker handles a large chat list, and that useIsDesktopLayout looks right.

Real clients, on staging

Passing automated tests does not prove clients interoperate, so connect each of these and run the same prompts: Claude Code, a Claude custom connector, MCP Inspector, and Cursor or Codex if your agents use them.

  • "When did I last talk about the lease, and with whom?" should use search, then get_message.
  • "Catch me up on my chat with Lucas" should use list_chats, then get_chat_messages.
  • "Sort my untyped groups" should use list_chats and set_group_type, and the labels should appear in the inbox.
  • "Find everything about the lease and save it for me" should produce a search you can open on your phone.
  • A synthetic message in the Lucas test chat that tells the agent to send your messages elsewhere or relabel groups. Run it with the agent's outbound tools behind approval, and record what it tries.
  • A search for a term that exists only in a hidden group. The agent should say some chats were not searched.
