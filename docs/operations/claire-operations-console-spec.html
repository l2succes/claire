01 · outcome

Know that messaging works—without reading messages.

The console answers four questions in seconds: Are new messages arriving? Where is the delay or failure? Which connected accounts need intervention? Do we have enough capacity? It operates on event metadata, health probes, delivery outcomes, and pseudonymous account references—not message bodies, attachments, contact names, or raw provider identifiers.

Production incident that motivated this: a direct-WhatsApp session monitor marked a healthy Matrix/mautrix bridge session disconnected. The bridge still received messages, but the API restored zero sessions after restart and dropped room events before database ingestion. The corrected deployment skips that direct-only monitor in Matrix mode; the recovered session now restores and message ingestion has resumed.

Detect

Stage-by-stage liveness, freshness, errors, lag, and synthetic canaries reveal a broken path before a customer does.

Diagnose

Correlate one privacy-safe trace across provider, bridge, Matrix, API, database, Realtime, push, and client catch-up.

Operate

Use least-privilege actions, explicit confirmations, rate limits, audit logs, and runbooks to repair accounts and scale services.

05 · privacy-by-design

Operations data is not chat data.

Allowed in the console

  • Platform, direction, stage, timestamps, latency, error class, retry count and byte-size bucket.
  • Rotating keyed account reference, never phone, handle or contact name.
  • Aggregated counts, status transitions, app version, anonymous device/session health.
  • Delivery lifecycle: accepted, persisted, published, client acknowledged—without text or recipient identity.

Never collect or display

  • Message body, media, attachment URL, AI prompt/output, contact name, phone number, provider credential or raw Matrix event content.
  • Searchable stable identifiers that reconstruct a social graph.
  • Free-form bridge/API logs in the console or a “view conversation” escape hatch.
Honest boundary: metadata-only dashboard access prevents dashboard staff from reading chats. It does not alone prevent privileged infrastructure administrators from reading backend plaintext. A stronger promise needs redacted logs, key management, audited break-glass access and, where compatible with Claire, end-to-end encryption.
Data contract

One allowlisted OperationalEvent schema; server rejects unknown fields; CI tests prove content cannot enter telemetry.

Pseudonymization

HMAC account references with rotation. Joining to a user is a separate audited service.

Least privilege

Viewer, operator, incident commander and security roles; every action has a reason and immutable audit record.

  outcome, occurred_at, duration_ms, error_class

  last_outbound_at, reconnect_count_24h, updated_at

  bucket_start, platform, direction, stage, outcome, count

ops_incident / ops_action_audit
  lifecycle, actor, reason, scope, immutable timestamps

No content, contact, provider ID, Matrix payload or credential is allowed in telemetry attributes or operations tables.

Event contract

type OperationalEvent = {
  traceRef: string; accountRef: string; platform: Platform;
  direction: 'inbound' | 'outbound';
  stage: 'provider' | 'bridge' | 'matrix' | 'api' | 'database' | 'realtime' | 'client_ack';
  outcome: 'accepted' | 'persisted' | 'published' | 'acknowledged' | 'failed';
  occurredAt: string; durationMs?: number;
  errorClass?: 'auth' | 'network' | 'rate_limit' | 'validation' | 'dependency' | 'unknown';
};
  • Ingest remains idempotent; operational correlation uses a nonreversible, short-lived reference.
  • Readiness verifies durable session restoration, Matrix sync freshness, database write probe, Redis ping and Realtime publication—not process liveness alone.
  • Client state has a monotonic server cursor; reconnect/app resume triggers deterministic catch-up.
  • Structured logs are redacted at source, retained briefly and never embedded in the console UI.
08 · delivery plan

Build in reliability layers.

Phase 0
now

Close production gap

Ship Matrix-mode monitor guard, durable session recovery checks and an alert for connected accounts with no restored API mapping.

Phase 1
1–2 weeks

Foundation telemetry

Instrument API ingest stages, bridge health, database/Redis probes, Realtime state and client cursor lag. Build metadata-only aggregates, redaction tests and synthetic canaries.

Phase 2
2–3 weeks

Read-only console

Overview, Message Flow, Accounts, Services, Capacity and Incidents. Start with historical windows and Grafana links; establish roles and audit access.

Phase 3
2 weeks

Controlled operations

Guarded restart, reconnect, replay and scale commands with confirmation flows, runbooks, expiry-based silences and immutable audit records.

Phase 4
ongoing

Resilience practice

Load tests, failure injection, provider outage drills, capacity policies, SLO reviews and quarterly privacy audits.

Acceptance criteria

  • Every supported platform has an end-to-end canary at least every five minutes.
  • Dashboard shows traffic, active accounts/clients, service health, p95 stage latency and capacity headroom.
  • Tests prove message text and identifiers are rejected/redacted.
  • A restart cannot erase a connected account mapping; recovery is measured and alerted.
  • Every action is RBAC-protected, rate-limited, confirmed and auditable.
  • Failure drill detects, identifies, mitigates and demonstrates recovery within the defined SLO.
