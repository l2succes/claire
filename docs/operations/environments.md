# Claire environments and release flow

| Purpose | Git branch | Website | API | Supabase gateway |
| --- | --- | --- | --- | --- |
| Production | `production` | `useclaire.co` | `api.useclaire.co` | `supabase.useclaire.co` |
| Staging | `main` | `staging.useclaire.co` | `api.staging.useclaire.co` | `supabase.staging.useclaire.co` |
| Review | pull request branch | Vercel preview URL | none | none |

The `production` branch is protected: changes arrive through pull requests,
stale reviews are dismissed, conversation resolution is required, and force
push/deletion are blocked. It intentionally requires zero approvals so its
sole operator is not locked out; add an approval requirement when another
maintainer is added.

## Vercel

The `claire-landing` project builds from `apps/website/`, with dependencies
installed from the monorepo root. Its production branch is `production`; the
apex domain and `www` redirect are configured. `staging.useclaire.co` is
attached to the Preview environment for `main`, and its DNS record is managed
at Spaceship. Push a new `main` commit and confirm the staging domain is
assigned to that preview deployment before treating a website release as
available.

## Release and rollback

1. Merge feature work into `main`; test fixtures and opt-in staging identities
   only.
2. Verify the staging website/API/gateway, Auth callbacks, CORS, RLS denial,
   private-media migration state, and backup restore evidence.
3. Open a pull request from `main` to `production`. The production deploy is
   triggered only after that merge.
4. To roll back, use Vercel's previous production deployment and Railway's
   known-good deployment. Do not roll back databases by restoring over the
   live database; use a tested, explicit restore procedure.

## Mobile clients

The EAS `preview` environment is Claire staging and EAS `production` is Claire
production. Expo Prebuild (Continuous Native Generation) generates the iOS and
Android projects from `apps/client/app.config.js`; those generated directories
are intentionally not tracked in Git.

| Build profile | App shown on the phone | iOS bundle ID / Android package | EAS environment |
| --- | --- | --- | --- |
| `development` | Claire Dev | `com.claire.app.dev` | `development` |
| `staging` | Claire Staging | `com.claire.app.staging` | `preview` |
| `production` | Claire | `com.claire.app` | `production` |

The distinct identifiers let Claire Staging and Claire run side by side on the
same phone. Each app has an isolated local session/cache and an environment
specific OAuth callback (`claire-staging://confirm` or `claire://confirm`).
Do not add a production/staging switch inside a distributed binary: endpoint
and authentication isolation must be selected by the build profile.

Mobile builds load their public routing values from EAS, not from Git. Set only
these client-readable values there:

- `EXPO_PUBLIC_API_URL`
- `EXPO_PUBLIC_SUPABASE_URL`
- `EXPO_PUBLIC_SUPABASE_ANON_KEY`
- `EXPO_PUBLIC_ENV`

The API URL and Supabase URL have been assigned to their environment domains.
The staging anon key must be generated by the isolated staging Supabase stack
before a staging build is distributed. Do not reuse the production anon key.
Never add a service-role key, database password, OAuth secret, or any operator
credential to EAS public variables.

```sh
cd apps/client
bun run start:staging
bun run build:staging
bun run build:prod
```

For a physical device, register it with EAS first, then open the EAS build's
install link on that device. Use `production-store` only for an App Store or
TestFlight submission; it is deliberately separate from the installable
internal `production` profile.

See [Expo and EAS mobile builds](./expo-builds.md) for device registration,
local Prebuild commands, private installation, and build recovery.
